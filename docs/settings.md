# settings.php and secrets

How every Drupal site we build handles its settings and secrets. The aim: every
change to how a site is configured has a history and goes through review, the file
that holds the secrets holds values only, and no secret is ever in git.

Background: on one client site, `hash_salt` was moved by hand from a file into
`settings.php`. The value lost the file's trailing newline, so the salt changed. A
login module linked accounts through a value derived from the salt, so every login
created a new account for six days. `settings.php` was kept out of git, so the change
had no history and the cause took six days to find. Keeping secrets in a separate
file doesn't stop such a mistake by itself: the values in it can still be changed by
hand. That is why the secrets file can't hold logic, why changes are checked against a
fingerprint, and why sites like that one stop when their salt changes.

## The rules

1. **`settings.php` is committed and holds all the logic.** The config sync directory,
   trusted host patterns, includes, what differs between environments, and which
   secrets map to which settings. It is reviewed in a pull request and deployed like
   any other code.
2. **On a server, the secrets are only in `.env.local`, in the project root**, next to
   `composer.json` and outside the docroot. It holds `KEY=value` lines only, so it
   can't change what the site does, only the values it uses. It is never committed and
   never deployed. `.env.example` is committed and lists every key.
3. **Vaultwarden holds the master copy of each server's `.env.local`.** There is one item
   per site and environment, named `<site> <ENV> .env.local`, with the whole file in
   its note. The file on the server is written from that item, never edited on its own.
4. **Every change to a server's `.env.local` is noted in the client's ticket**: what
   changed, why and when. Never the value. This is the only history the secrets have.
5. **Environments differ by `DRUPAL_ENV` only** (`dev`, `test` or `prod`). `settings.php`
   decides what that means, e.g. which Config Split is on.
6. **`settings.local.php` is for local development only.** On a server, the site
   refuses to start if one exists.
7. **A site where a module stores values derived from `hash_salt` commits the salt's
   fingerprints** (see [hash_salt](#hash_salt)). The site then refuses to start when
   its salt has changed.

| What | Where | In git |
|---|---|---|
| Config sync directory, trusted hosts, environment differences, other settings | `settings.php` | Yes |
| Which keys a server needs | `.env.example` | Yes |
| Reading `.env.local` | `settings.env.php`, included from `settings.php` | Yes |
| Database credentials, `hash_salt`, API keys, passwords | `.env.local` on each server | No |
| Local database and `hash_salt` | `settings.ddev.php`, generated by DDEV | No |
| Local development overrides | `settings.local.php`, in DDEV only | No |

## How it works

`setup.sh` adds `vlucas/phpdotenv`, `.env.example` and
`web/sites/default/settings.env.php`, and wires them into `settings.php`:

```php
if (getenv('IS_DDEV_PROJECT') == 'true' && file_exists(__DIR__ . '/settings.ddev.php')) {
  include __DIR__ . '/settings.ddev.php';
}
$settings['config_sync_directory'] = '../config/sync';
include __DIR__ . '/settings.env.php';
// The site's own settings, which can map further keys from $env_local.
if (file_exists($app_root . '/' . $site_path . '/settings.local.php')) {
  include $app_root . '/' . $site_path . '/settings.local.php';
}
$settings['hash_salt_sha256'] = [
];
// ... the hash_salt check, last.
```

Outside DDEV, `settings.env.php` reads `.env.local` with `Dotenv::parse()`, which
returns the values without putting them in the process environment, so they don't
show up in `phpinfo()`. Unlike Symfony's Dotenv, it never runs `$(...)` commands. It
then sets the database and `hash_salt` from `DB_NAME`, `DB_USER`, `DB_PASSWORD`,
`DB_HOST` (default `localhost`), `DB_PORT` (default `3306`) and `HASH_SALT`. The site
refuses to start when `.env.local` or a required key is missing.

Further secrets go the same way: add the key to `.env.example`, to each environment's
Vaultwarden item and `.env.local`, and map it in `settings.php`:

```php
$config['example.settings']['api_key'] = $env_local['EXAMPLE_API_KEY'] ?? '';

if (($env_local['DRUPAL_ENV'] ?? '') === 'prod') {
  $config['config_split.config_split.prod']['status'] = TRUE;
}
```

**Writing values.** Put values in single quotes (`DB_PASSWORD='p#ss w0rd'`): then
nothing in them is interpreted. Spaces at the end of an unquoted value are dropped.
Double quotes are only for a value that has to end with a newline (`"...\n"`).

## Locally (DDEV)

DDEV writes the database credentials and a `hash_salt` to `settings.ddev.php`, which
`settings.php` includes only inside DDEV, and which DDEV keeps out of git. A fresh
install writes nothing secret to `settings.php`: `hash_salt` stays `''` and
`$databases` stays empty. A local `.env.local` is optional, for keys such as a test
API key. Settings for local development, e.g. from
`web/sites/example.settings.local.php`, go in `settings.local.php`.

`setup.sh` warns when `settings.php` is ignored by git or sets `hash_salt` or a database
password, and when `.env.local` or a `settings.local.php` is tracked by git.

## On a server (DEV, TEST, PROD)

`.env.local` lives in the project root. With atomic releases it lives in the shared
directory and is linked into each release. The deploy never writes or deletes it.

### Creating .env.local

1. Create the Vaultwarden item `<site> <ENV> .env.local` from `.env.example`, with the
   environment's values. For a new site, generate the salt once with
   `ddev drush php:eval 'echo \Drupal\Component\Utility\Crypt::randomBytesBase64(55), PHP_EOL;'`.
   Each environment gets its own salt.
2. Write the file on the server as the user that owns the site's files. Paste the
   note's content between the `ENV` lines:

   ```sh
   sudo -u <site-user> tee /<project-root>/.env.local > /dev/null <<'ENV'
   <the note's content>
   ENV
   sudo -u <site-user> chmod 0440 /<project-root>/.env.local
   ```

   The quoted `'ENV'` keeps the shell from changing `$` and backslashes in the
   content. If PHP-FPM runs as another user, it needs to be able to read the file
   (group `www-data` with `0440`, for example).
3. Check that the site starts:

   ```sh
   sudo -u <site-user> /<project-root>/vendor/bin/drush --root=/<project-root> status --field=bootstrap
   ```

   It should print `Successful`.

### Changing .env.local

1. Keep a copy of the current file and note the fingerprint of the effective salt:

   ```sh
   sudo -u <site-user> cp -p /<project-root>/.env.local /<project-root>/.env.local.bak
   sudo -u <site-user> /<project-root>/vendor/bin/drush --root=/<project-root> php:eval 'echo hash("sha256", \Drupal\Core\Site\Settings::getHashSalt()), PHP_EOL;'
   ```

2. Change the Vaultwarden item, then write the file from it as when creating it.
3. Run the `drush php:eval` command again. The fingerprint must be identical, unless
   the change was a planned salt change. If it differs, put the copy back and find out
   why before going on:

   ```sh
   sudo -u <site-user> mv /<project-root>/.env.local.bak /<project-root>/.env.local
   ```

4. Check that the site starts, as when creating it, then delete the copy:

   ```sh
   sudo -u <site-user> rm /<project-root>/.env.local.bak
   ```

5. Note the change in the client's ticket.

## hash_salt

**Keep it permanent on a live site.** On most sites a changed salt does little
lasting harm: image style URLs in cached pages, forms that are open and one-time
login links stop working until caches are rebuilt. On a site where a module stores
values derived from the salt, such as the login module in the background above, a
changed salt silently breaks that data.

**On such a site, turn on the hash_salt check.** A fingerprint is the sha256 of the
salt: it identifies the value without revealing it, so it can be committed.

1. On each server, print the fingerprint of the salt the site uses:

   ```sh
   sudo -u <site-user> /<project-root>/vendor/bin/drush --root=/<project-root> php:eval 'echo hash("sha256", \Drupal\Core\Site\Settings::getHashSalt()), PHP_EOL;'
   ```

2. Add it to the list at the end of `settings.php`, under the server's `DRUPAL_ENV`. The
   key decides which server the fingerprint belongs to, not the order:

   ```php
   $settings['hash_salt_sha256'] = [
     'dev' => '<what step 1 printed on DEV>',
     'prod' => '<what step 1 printed on PROD>',
   ];
   ```

3. Merge it in a pull request and deploy it as usual.

Outside DDEV, the site then refuses to start, with an error in the PHP log, when its
salt doesn't match the entry for its `DRUPAL_ENV`, or when that entry is missing. So a
new environment gets its entry before its first deploy, and a planned salt change is
a pull request with the new fingerprint, merged before the new salt is written on the
server. On other sites the list stays empty and nothing is checked. Check for such
modules when a site is set up and when one is added.

**When a site reads the salt from a file today** (`file_get_contents(... 'salt.txt')`),
copy its exact content into `HASH_SALT`, including a trailing newline, with
`HASH_SALT="...\n"`. See what the file holds with `xxd salt.txt`, and compare the
fingerprint before and after: an editor doesn't show a trailing newline or space.

## Moving an existing site to this routine

The routine applies to new sites. Existing sites are not moved as a project of its
own. This is the recipe for when one is rebuilt or the client asks for it. Do it in a
ticket of its own, per site.

1. On a branch, run `setup.sh`, or add `vlucas/phpdotenv`, `.env.example` and
   `settings.env.php` by hand. Start `settings.php` from the one on PROD and compare it
   with the other environments'. Remove everything secret from it: those values go
   in `.env.local`. Express the differences between environments with `DRUPAL_ENV`.
   Include `settings.env.php` as shown above. If no module stores values derived
   from `hash_salt`, leave the fingerprint list empty.
2. Take `settings.php` out of `.gitignore` and make sure `/.env.local` is in it.
   `setup.sh` adds the rule and warns about anything left.
3. Create the Vaultwarden item for each environment from that server's current
   values. Copy `hash_salt` byte for byte, as described above. Note each server's
   salt fingerprint, and commit them if the site needs the check.
4. Merge the pull request as usual. Before the release reaches each server:
   1. Write `.env.local` on the server. The old `settings.php` ignores it, so the site
      keeps working until the release replaces it.
   2. Remove the server's `settings.local.php`, if it has one, once its content is in
      `.env.local` or in `settings.php`. Do it right before the deploy: the old
      `settings.php` may still read it.
   3. If the deploy tool writes `settings.php` (a DeployHQ config file, for example),
      remove that from its configuration in the same release.
5. After the deploy, check that the site starts and that the salt fingerprint is
   unchanged. Note the change in the client's ticket.
